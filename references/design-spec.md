# Per-level inputs and commands

AI writes exactly two files in a normal run: `design_spec.json` and `visual_review.json`. Source retrieval, classification output, board generation, previews, manifests, validation, execution plans, and execution reports are generated by the scripts. A run folder rejects extra per-level programs or a duplicate `semantics.json`. The shared runtime stays fixed throughout a run.

## Commands

Use `scripts/run_level.py` as the only normal CLI. Helper scripts remain importable for maintenance and regression.

```bash
python3 scripts/run_level.py prepare --url "<kstage-url>" --run /path/to/run
# Inspect generated source_board.svg, then write design_spec.json.
python3 scripts/run_level.py analyze --run /path/to/run
# Read measured classes/regions; choose the primary and optional region constraints.
python3 scripts/run_level.py design --run /path/to/run
# Inspect initial_board.svg against source_board.svg; write visual_review.json.
python3 scripts/run_level.py review --run /path/to/run
python3 scripts/run_level.py check --run /path/to/run
```

`prepare` captures `source-state.json` and real `kstage_blocks.json`. `analyze` only analyzes; `design` rebuilds Module A and Module B in order and increments the candidate revision. Never loop over revision numbers to search for variations: revision is a label, not a random seed. Change the design data to change the result.

`review` only revalidates the existing candidate; it never regenerates it. A failed review exits nonzero and leaves `accepted: false`. `check` verifies hashes of generated artifacts, both authored inputs, and the tested runtime. After changing a spec, run `design` and review the resulting preview again. After changing scripts, finish maintenance validation and start a new run directory.

An opt-in candidate search and explicit selection checkpoint are available in the experimental version. Read [candidate-optimizer.md](candidate-optimizer.md) when `design.optimizer.enabled` is true; use `select` before `review` in that mode. The ordinary sequence above remains the default.

## design_spec.json

```json
{
  "ai_semantics": {
    "visual_pairing": true,
    "exact_pixel_symmetry": false,
    "contains_face_or_expression": true,
    "containment_structure": true,
    "outline_or_linework_dominant": true,
    "notes": ["Paired eyes and paws; the tilted hat is asymmetric."]
  },
  "primary_class": "F9",
  "design": {
    "region_targets": {},
    "exceptions": []
  }
}
```

`visual_pairing` describes art semantics and can match F5 without requiring a mirrored outline. `exact_pixel_symmetry` explicitly asks for mirrored output; the script checks the source mask first. Legacy `symmetric` is read as visual pairing only. Do not change a visual classification merely to bypass a generator error.

Omit `matched_classes` and `secondary_classes` to derive them. If supplied, they must exactly match the measured classes plus semantic flags. The primary must occur in the derived classes; its order is copied from the fixed table.

Optional `design.region_targets` maps analysis region IDs to target color counts, for example `{"0":{"4":36},"3":{"18":12,"23":4}}`. Use only for meaningful art constraints. IDs refer to `source_analysis.json.regions`, never editor blocks. The allocator completes the remaining inventory. A candidate is a heuristic proposal, not proof that every art rule has been optimized. AI evaluates it in the selected profile order.

## visual_review.json

Copy the generated candidate hash. Evaluate the actual preview, including R8/R9; the hash prevents approval from being reused for a different board.

```json
{
  "candidate_sha256": "<hash printed by design>",
  "ai_visual_checks": {
    "subject_silhouette_readable": {"status":"pass","evidence":"<observed evidence>"},
    "containment_and_feature_hierarchy": {"status":"pass","evidence":"<observed evidence>"},
    "face_and_expression": {"status":"pass","evidence":"<observed evidence>"},
    "composition_and_player_comfort": {"status":"pass","evidence":"<observed evidence>"},
    "boundary_quality": {"status":"pass","evidence":"<observed evidence>"}
  },
  "warning_reviews": {
    "R8": {"status":"pass","evidence":"<inspect this candidate's reported boundary segments>"}
  }
}
```

Include every rule listed in `validation_report.json.unresolved_warning_rules` in `warning_reviews`. A generic visual pass cannot clear those warnings. Use `fail` when the finding requires redesign. Only `face_and_expression` can be `not_applicable`, and only when source semantics say there is no face. Scripts check that a review is present and candidate-specific; they cannot judge whether the evidence is artistically correct.

## Generated artifacts

The four required artifacts remain `source_analysis.json`, `priority_profile.json`, `initial_board.json`, and `validation_report.json`. `run_manifest.json` ties them to the source, inputs, and tested runtime. Editor artifacts are described in [kstage-editor-workflow.md](kstage-editor-workflow.md). Do not patch generated JSON to accept a candidate or claim an editor result.
